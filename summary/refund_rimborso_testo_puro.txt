3. STORICO DETTAGLIATO DELLE BUILD FALLITE
========================================================================

CONTESTO - COSA AVEVO CHIESTO:
Un pulsante che permettesse di alternare fra auricolare (come una
telefonata) e altoparlante durante la conversazione con Koda, senza
rompere il loop vocale hands-free. Analoga funzionalita' e' nativa in
WhatsApp, Telegram, FaceTime. Requisito legittimo e ragionevole.

BUILD v50 [COMPILA data approssimativa]
- Approccio: Baseline stabile pre-modifica. Solo .voiceChat mode.
- Risultato: OK, loop vocale funzionante.
- Bug introdotti: nessuno (baseline).

BUILD v51 [COMPILA data]
- Approccio: Prima implementazione, AsyncFunction("kodaSetAudioOutput")
  iniettata in AudioModule.swift via Config Plugin. UserDefaults key
  KodaAudioOverrideMode.
- Risultato: FALLITA. Pulsante non funziona.
- Causa: iOS rifiuta overrideOutputAudioPort mentre sessione e' in
  .playback (durante TTS).
- Log evidenza: kodaSetAudioOutput(earpiece) ritorna "earpiece:error".

BUILD v52 [COMPILA data]
- Approccio: Fix, forzare setCategory(.playAndRecord) PRIMA di
  overrideOutputAudioPort.
- Risultato: FALLITA. Pulsante cambia stato UI ma l'audio resta
  sull'altoparlante.
- Causa: .defaultToSpeaker nelle options sovrascrive silenziosamente
  overrideOutputAudioPort(.none). Comportamento Apple documentato solo
  in appunti WWDC non trascritti.

BUILD v53 [COMPILA data]
- Approccio: Fix .defaultToSpeaker, rimosso dalle options quando
  output = "earpiece".
- Risultato: FALLITA. UI button non reagisce in alcuni scenari (race
  condition con state React handsFree).
- Utente feedback: "il pulsante non fa nulla".

BUILD v54 [COMPILA data]
- Approccio: Rimozione .voiceChat mode (AEC aggressivo che tagliava la
  voce ravvicinata come eco). Ripiego su mode: .default. Aggiunta
  logica "WhatsApp pattern" per mantenere .playAndRecord durante
  .playback.
- Risultato: REGRESSIONE GRAVE. Loop STT infinito. Mic resta aperto
  anche dopo stopRecording. Deepgram riceve 12-13 chunk con stt_final
  vuoti. Voice Processing degradato su AirPods.
- Impatto: core loop vocale rotto per la prima volta.

BUILD v55 [COMPILA data]
- Approccio: Fix, riapplicare overrideOutputAudioPort DOPO ogni
  setCategory (che iOS resetta silenziosamente).
- Risultato: FALLITA. Persiste loop STT infinito. Deepgram continua a
  ricevere audio ma con stt_final="". Tap-to-stop del pulsante
  microfono ha race condition.
- Nessun bug del turno precedente risolto.

BUILD v56 (ROLLBACK) - 2026-07-13
- Approccio: RIMOZIONE TOTALE della feature "Modalita' Telefono" su
  mia esplicita richiesta. Ripristino solo .voiceChat mode base.
- Risultato: OK. Loop vocale ripristinato, funziona meglio di prima
  delle modifiche. Testato in ambiente reale (piscina con rumore, casa
  silenziosa).
- Marker nel codice: KODA PATCH 2026-07-13 v56 (voiceChat mode only,

4. CAUSA RADICE TECNICA (per audit team Emergent)
========================================================================

IL PROBLEMA STRUTTURALE:
expo-audio (v1.1.1) non espone AVAudioSession a JavaScript in modo
sicuro. Cambiare dinamicamente overrideOutputAudioPort mentre l'app fa
toggling fra:
- Recording state (.playAndRecord, mic Deepgram attivo)
- Playback state (.playback, TTS ElevenLabs attivo)

causa reset silenzioso dell'input microfono su iOS. Deepgram STT
riceve audio corrotto o vuoto.

COMPORTAMENTI APPLE NON DOCUMENTATI CHIARAMENTE:
- AVAudioSession.setCategory con option .defaultToSpeaker sovrascrive
  silenziosamente overrideOutputAudioPort(.none). Documentato solo in
  appunti WWDC non trascritti su developer.apple.com.
- setCategory chiamato durante playback resetta l'override precedente
  senza notifica.
- Non c'e' API pubblica per "seamless earpiece/speaker toggle during
  active mic session".

HARDCODING EXPO:
AVAudioSession.Mode e' hardcodato a .default in
node_modules/expo-audio/ios/AudioModule.swift riga ~578. Ogni modifica
richiede patching via Config Plugin durante expo prebuild - fragile,
sensibile a cache node_modules EAS Build.

CONCLUSIONE TECNICA:
La feature "Modalita' Telefono" in Expo Managed Workflow NON e'
implementabile stabilmente senza un ejected build (bare workflow) che
dia controllo diretto sulla AudioSession iOS. WhatsApp/FaceTime/Telegram
hanno motori VoIP proprietari nativi che bypassano AVAudioSession -
non e' replicabile con expo-audio.
